For the engineering team — the blueprint contract, and why the count is five

A blueprint is a governed, self-contained unit: a CloudFormation template, the four mandatory cornell:* tags, a baseline monthly cost, and a permitted data classification — all declared in a blueprint.yaml manifest. The rule is "no manifest, no catalog entry".

Seven directories, five publishable. course-chatbot and entra-probe hold only infra/ and a README — no manifest. blueprint_search globs blueprints/*/blueprint.yaml, so those two cannot appear in the catalog and cannot be deployed today. An independent check confirmed both manifests return HTTP 404 from the GitHub API. We report five so the number matches what a user can actually get.

Of the five, hello-world, knowledgebase and notify-topic are singletons — the deployment name is forced to the blueprint name. aisei-site and tiny-chatbot accept a custom name.

08 · Why leadership can trust it

Four things it can never do

These are permanent guarantees, not today's limitations. They hold for every tool, and they are why we can point an AI tool at a shared cloud account at all.

✕ It can never approve its own request

Approval is a human act. There is no setting, no permission and no second attempt that lets the tool approve anything itself.

✕ It can never edit the official copy directly

Every change arrives as a separate proposal that someone has to accept. The review step cannot be stepped over.

✕ It can never create, change or destroy cloud resources

That permission belongs to the platform team's own system, which acts only after a person approves. Even shutting something down is a request that gets reviewed.

✕ It never puts passwords or keys on your laptop

Your machine holds nothing. If access ever needs to be revoked, that happens centrally and immediately.

One sentence for the risk register

Something gets built exactly one way: a person approves the request, and that approval is what builds it. Everything the Builder does before then is either reading, or writing a proposal.

For the engineering team — the exact wording, and where it is enforced
  • Never merges a pull request. Not with a token, not with elevated rights, not by asking twice.
  • Never pushes to a tracked branch. Every change is a new branch plus a pull request; main is never written to directly.
  • Never calls CloudFormation Create, Update or Delete. That belongs to the platform pipeline, which acts only on a merge. Deletion is a pull request too.
  • No credential on the client. No AWS keys, no git token on the researcher's laptop. The server process holds what it needs.

The only two AWS writes anywhere in the system are starting a pipeline execution and retrying a failed stage — neither can change what gets deployed.

Written down in packages/builder-mcp/SPEC.md (C3, C5) · AWS permissions in packages/builder-mcp/infra/builder-mcp.yml · tool-by-tool evidence in packages/builder-mcp/docs/tool-verification.html · tests in packages/builder-mcp/tests.

13 · Honest constraints developer-oriented

Five things that will bite, in the order they will bite

All measured, none hypothetical. The first has already caught people out in a demo.

1 · About six searches an hour, shared across all of campus

Anonymous GitHub API access costs ~9 requests per catalog search (one directory listing plus one per catalog entry) against a 60 requests/hour per-IP ceiling. That is about six searches an hour. On a shared campus NAT, everyone behind that address shares the same 60. A token raises the ceiling to 5,000/hour.

0reqs / search
0anon / hour
0with token

2 · Without a GitHub account set up, nothing real is created

Without a GitHub token, every write tool returns a plan instead of opening a pull request. This is by design and is documented — and it still surprises people, because the plan looks like success. If a demo "creates a deployment" and no PR exists, this is why.

3 · It only ever sees the official copy

The catalog fetch reads the repository's default branch. There is no branch override. An installed plugin therefore sees main regardless of which branch you are working on — so a blueprint you just wrote on a feature branch is invisible to the tool until it merges.

4 · uv must be installed locally

The plugin launches the server through uv. Its absence is an install-time failure, deliberately loud rather than a silent tool-less session — but it is a prerequisite on every machine, and one more thing to put in the onboarding instructions.

5 · Checking whether it is live still needs cloud access

Creating a deployment needs no AWS credential. Watching it does: stack status, pipeline stages and health checks are real AWS reads. Without credentials those tools degrade to a clear error rather than a lie — but "is my thing live yet?" goes unanswered.

Where these are written down

Rate-limit measurement and the token policy: packages/builder-mcp/plugin/SPEC-PLUGIN.mdNEW (P2, P4). Degradation behaviour: packages/builder-mcp/SPEC.md (C5). Known gaps and agreed-but-unbuilt work: packages/builder-mcp/BACKLOG.md and packages/builder-mcp/ROADMAP.md.

14 · Today vs aspirationally

Today this needs a developer. The goal is that it will not.

The design target is a researcher with no CloudFormation knowledge. That is not who can use it this afternoon, and pretending otherwise would set the pilot up to fail.

Today · a developer or a technically confident RSE

Someone who already has:

  • Claude Code or Cowork installed and working.
  • Comfort with uv, a terminal, and a package manager.
  • A GitHub account, and the judgement to create and scope a token.
  • Enough fluency to read a pull request diff and tell whether it says what they meant.
  • AWS credentials, if they want to watch the deployment progress.

The goal · a researcher with no technical background

Someone whose entire interaction is:

  • Describe the thing they want, in their own words.
  • Read a plain-language plan and a cost, and say yes.
  • Get told when it is live, and be able to ask why if it isn't.

Nothing in the architecture prevents this. The gap is entirely in setup, identity and support.

15 · Bridging the gap

The hard part is not the software. It is the review queue.

The Builder deliberately routes everything through a human merge. That is the security model — and it means the system's throughput is set by how many people can review, and how quickly. This is a staffing and training question, not an engineering one.

Who must be trained

  • Builders — that a plan is not a deployment, and that a pull request needs a human before anything happens.
  • Reviewers — what a well-formed registration pull request looks like, and which three or four things actually need checking.
  • Blueprint authors — the manifest contract, the mandatory tags, and the traps that produce a green pull request that deploys nothing.
  • Platform operators — inventory, cost attribution and teardown, all of which depend on tagging discipline holding.

Who must approve

  • A second person on every pull request — nobody approves their own.
  • The platform team owns the shared AWS account, the pipeline and the secrets. That does not move.
  • Security signs off the model once, not per deployment — the exportable security spec exists precisely to make that repeatable.
  • Data governance decides which classifications a blueprint may carry; the tool enforces the answer, it does not make it.

Why the gate is a feature

Removing the human merge would remove the entire safety argument. The correct response to a slow queue is more reviewers and smaller diffs — never an automated merge. Every design choice so far pushes in that direction: one-action insertions, conventional stack names, readable diffs.

A reviewer's stated fear is an unreviewable diff. Keeping diffs small is how we protect the queue.

Growing reviewer capacity — the plan, in escalating order

1

Make review cheap. Small, conventional pull requests that a trained reviewer reads in minutes. Already the design.

2

Automate the checkable part. Convention, registration and template validity are already machine-checked, so humans spend their attention on judgement, not syntax.

3

Train a reviewer cohort per college or unit. Reviewing does not require platform-team membership — it requires knowing what to look for. Publish that checklist.

4

Tier by risk. A zero-cost, public-data blueprint and a stack holding student records do not warrant the same scrutiny. Classification is already in every manifest; use it to route.

Risks to name out loud

  • Catalog starvation — already recorded as a high risk. A catalog that doesn't cover what people ask for makes the tool feel broken.
  • Reviewer bottleneck — a fast requester queued behind a slow gate is a worse experience than the ticket it replaced.
  • Orphaned deployments — owners graduate and leave. Teardown must be as governed as creation, and it is: deletion is a pull request too.
  • Over-trust — an approved plan that nobody actually read is the failure mode to design against.

What we are not asking for

  • No new AWS access for researchers. The credential boundary does not move.
  • No change to who owns the shared account.
  • No bypass of security or data-governance review.
  • No new approval body — the reviewers are the ones already approving pull requests.

The ask is trained reviewers, a named support path, and permission to pilot.

One willing researcher with a real need, not a demo. The point is to find out which of the gaps actually blocks them, rather than which ones we assume will.

Appendix · categories 1 and 2 open questions, not failures

Can it understand real people, and does it know who they are?

The first two risk categories sit at opposite ends of the same request: what the user typed, and whether they were allowed to type it.

R1 Category 1 · language

Linguistic variability

How resilient are the tool calls and prompt wrappers to language that is not clean, standard English? Typos, grammatical errors, non-native phrasing, and the compressed half-sentences a student actually types into a syllabus bot at 11pm. Our own testing has been done by people who write like the documentation.

Open question: what is the failure mode when a query is understood approximately rather than exactly — a wrong-but-plausible blueprint match, or a clean "I'm not sure what you mean"?

OPEN

R2 Category 1 · language

Prompt specificity battery

There is no structured test battery benchmarking reliability across a spectrum of prompt clarity — from vague and ambiguous ("I need an AI thing for my class") through to hyper-specific structured instruction. Without one, "it works" means "it worked for the phrasings we happened to try".

Open question: what does the reliability curve look like as prompts get vaguer, and where on that curve does it become unsafe rather than merely unhelpful?

OPEN

R3 Category 2 · identity

Access control scope per deployment tier

A public, student-facing service and an internal staff workflow do not warrant the same authentication posture, and we have not decided what each tier should require. The server's inbound authentication currently runs in an open testing-phase mode with an institutional identity path designed and stashed behind a switch — the decision about which tier gets which has not been made.

Open question: what is the minimum acceptable auth for each deployment tier, and who signs that off?

DESIGNED, NOT DECIDED  See C5 in packages/builder-mcp/SPEC.md

R4 Category 2 · identity

Identity context passing, before execution

User identity and role-based permissions must be verified before the server executes a downstream action or retrieves restricted context — not after, and not as a display-only field. The known gap is real and documented: the production authentication path carries application identity, whereas per-user NetID identity requires a different flow that is on the backlog, not built.

Open question: until per-user identity lands, what may a deployment be allowed to retrieve on a user's behalf?

Appendix · categories 3 and 4 open questions, not failures

Can people experiment safely, and can the tool be pushed off its job?

Categories 3 and 4 are about what happens either side of a correct request: safe failure before it, and boundary enforcement during it.

R5 Category 3 · fail fast

A rapid-iteration sandbox

Non-technical faculty and staff need somewhere to fail fast — to try a thing, watch it not work, adjust, and try again — with no downstream consequence and no reviewer's time consumed. Today the closest equivalents are the dry-run plan and a local preview tool that renders exactly what a deployment pull request would deploy without calling AWS or GitHub. Both are developer-facing.

Open question: what does a low-stakes sandbox look like for someone who will never open a terminal?

SEAM EXISTS, NOT PRODUCTISED  packages/builder-mcp/devtools/preview_deploy.py

R6 Category 3 · fail fast

Cost and vulnerability guardrails

An unmonitored live deployment can quietly run up model or API costs, consume cloud resources, or expose a vulnerability simply by being exposed too early. Every blueprint declares a baseline monthly cost and what that cost scales with, and that figure is shown before a deployment is proposed — but there is no ceiling, no alerting threshold, and no automatic stop.

Open question: who is notified, and what happens automatically, when a pilot deployment's spend or exposure crosses a line?

ESTIMATED, NOT ENFORCED  C1 cost block, packages/builder-mcp/SPEC.md

R7 Category 4 · intent boundary

Diverting and misaligned workflows

Tool definitions need hardening so a user cannot pull the tool away from its intended domain — whether by deliberate prompt injection or by ordinary operational drift, which is the more likely of the two. The governance invariants put a hard floor under the worst case: no merge, no push, no CloudFormation write, no credential on the client. What they do not constrain is how far a request can wander within those limits.

Open question: what is the test that proves a tool refuses an off-domain instruction, rather than a reviewer noticing later?

FLOOR EXISTS CEILING OPEN

R8 Category 4 · intent boundary

Scope locking

An agent built for one domain — syllabus questions and answers, say — must not be manipulable into off-scope or privileged actions. This applies to the deployments the Builder creates at least as much as to the Builder itself: a chatbot blueprint deployed forty times is forty chances for scope to be tested by someone curious.

Open question: should scope constraints be a declared, reviewable field on the blueprint contract, the way cost and data classification already are?

Appendix · category 5 · what are we not thinking about?

Four more, starting with the biggest omission

Raised in answer to the project lead's question. Two of these already have a real partial answer built in, which is worth saying out loud.

R9 Biggest omission

Data classification & regulatory compliance

A student-facing syllabus bot touches FERPA-protected records the moment a student asks about their own work. Research workloads can raise HIPAA, export control, or IRB obligations on top. Regulatory exposure is not a cloud problem, it is an institutional one, and it is the fastest way for a promising pilot to be stopped.

Good news, and it is genuinely good: this is partly built. The blueprint contract C1 carries a data_classification field on every blueprint, and the review gate blocks anything above the declared level. The mechanism exists; what is missing is the institutional mapping from Cornell's classification vocabulary onto it, and a decision about who owns that mapping.

MECHANISM BUILT POLICY MAPPING OPEN  C1, packages/builder-mcp/SPEC.md

R10 Category 5

Auditability & attribution

Who asked for this, who approved it, who deployed it — and can we reconstruct why eight months from now, when the person who asked has graduated and the person who approved has changed roles?

Strong story here. Because every deployment is a merged pull request, the audit trail is permanent, attributable and already exists — the request, the plan, the reviewer, the timestamp and the discussion are all in one place by construction, not by anyone remembering to log it. Pair that with the mandatory cornell:deployment-id tag as the join key between the git record and the running resource, and the chain is complete from utterance to instance.

LARGELY SOLVED BY CONSTRUCTION  Tag requirements: blueprints/README.md

R11 Category 5

Lifecycle, offboarding & orphaned resources

The classic university cost leak. A grant ends. A student graduates. A PI moves institution. The infrastructure keeps running, nobody owns it, and it surfaces two years later as a line item nobody can explain. Orphaned deployments are already recorded as a platform-operator fear.

The seam exists; the process does not. The spec-export tool already has offboarding and transfer audiences, so a deployment can write its own handover document on request, and deletion is a governed pull request rather than an untracked console click. What is missing is entirely organisational: nobody is scheduled to ask the question.

SEAM EXISTS, PROCESS MISSING

R12 Category 5

Cost attribution & chargeback

Distinct from the runaway-spend guardrails in category 3. That question is "how do we stop it"; this one is "whose budget is this?" Departments, grants and cost centres all need to see their own spend, and a shared account with no attribution model becomes one central bill that nobody will agree to pay.

The hook is already mandatory: every resource carries a cornell:owner tag, so per-owner spend is derivable today. What does not exist is the mapping from an owner NetID to a cost centre, or any agreement about who is charged.

R13 Category 5

Evaluation as continuous regression, not a one-time battery

The prompt-robustness battery in category 1 only holds its value if it runs on every change. A battery run once produces a number for a slide; a battery run on every commit produces a guarantee. Without that, robustness decays silently — nobody breaks it deliberately, it just erodes as prompts and tool descriptions are edited, and nobody finds out until a user does.

Worth knowing: tooling for scored plugin evaluations already exists, so this is a wiring-up job rather than a build-from-scratch one. The existing test suite is the natural place to hang it.

OPEN  packages/builder-mcp/tests

R14 Category 5

Degradation UX — correct, but silent

The category where the system is behaving exactly as specified and the user cannot tell. We already have a live example, on the bottlenecks slide: with no GitHub token every write tool returns a dry-run plan instead of opening a pull request. That is correct by contract C5, it is documented, and it still reads as success to someone who does not know to look.

The generalisable lesson: correct-but-silent is a usability defect, not a documentation problem. Every degraded mode we add needs an answer to "how does the user find out?" written at the same time as the mode itself.

R15 Category 5

Support model & escalation

Who does a faculty member call at 9pm the night before term starts, when a deployment they were relying on has failed? Right now the honest answer is "whoever they happen to know on the team". Unowned support is how promising internal tools die — not dramatically, but by two or three people quietly deciding it is not dependable enough to build a course on.

This is the same ask as the change-management slide, restated as a risk: a named owner, a response expectation, and an escalation path for the case where the pipeline itself is the problem.

R16 Category 5

Accessibility

Anything student-facing carries a legal accessibility obligation for the university, and blueprints that ship a user interface inherit that obligation the moment they are deployed at scale. It is far cheaper to put accessibility requirements into the blueprint contract once than to retrofit forty deployments that all copied the same inaccessible starting point.

Open question: should a blueprint that ships a user-facing interface be required to declare its accessibility posture, the same way it declares its cost and its data classification?
