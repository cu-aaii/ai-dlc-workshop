Cornell AI-SEI · Product Proposal · Draft for discussion

Cornell Builder
from a two-day demo to a platform product

How to turn the August 3–4 workshop chain into a service units actually adopt — the architecture, the one primitive that decides everything, a four-phase build, and the eight decisions that need answers before September.

01The product thesis

The product is a paved road, not an AI feature. Cornell has no sanctioned way to get custom software into production. Units build what they need wherever they can, and central IT finds out afterward — at audit, at incident, or at renewal. The proposal is to build the road: a catalog of governed, versioned infrastructure blueprints, a plain-language front door onto it, one unbypassable review gate, and a single inventory of everything that came out the other end.

Adoption follows one rule and only one: the sanctioned path has to be faster than going around it. Every decision below is downstream of that. A governed path that takes three weeks loses to a departmental credit card every time.

The workshop MVP proves the chain is possible. It does not prove it is a product. The gap between those two things is roughly nine months of work, and most of it is not the AI part — it is versioning, tenancy, policy enforcement, and the operating model that keeps a catalog alive after the people who built it move on.

02Scope: what this is and isn't

What it is

  • A catalog of versioned, pre-governed infrastructure blueprints
  • A conversational front door that maps intent to blueprints and gathers the parameters
  • A single governance gate every deployment passes through
  • An inventory of every deployment, its owner, health, and cost
  • A contribution model so units extend the catalog rather than queue for it

What it is not

  • Not a low-code app builder — it provisions infrastructure, it does not write your business logic
  • Not an AI product — AI is the interface and the codegen, not the point
  • Not a replacement for unit engineering teams — it removes their undifferentiated work
  • Not a hosting service that central IT operates on units' behalf
  • Not a mandate on day one — mandates before the road is faster produce shadow IT, not compliance

03Architecture: five planes

The system is a stack, not a pipeline. The builder touches exactly one plane; the other four are the product's actual substance and are deliberately invisible to them. Drawing it this way makes the load-bearing claim explicit — everything below the fold is abstracted, and each plane can be replaced without disturbing the one above it.

Correction to the workshop model

Code generation happens in the builder's own client, not server-side — which is cheaper than it sounds, but means the client cannot hold a git credential if "no direct write access" is to mean anything. The MCP server should expose propose_change, take a diff, and commit through a GitHub App installation. The builder's identity never enters the credential chain.

04The primitive that decides everything

One design choice determines whether this is a platform in three years or a pile of forty unmaintainable forks: what exactly is a blueprint?

GitHub template repositories copy code at instantiation. Once forty units have made a course chatbot, a security fix to the template reaches none of them — you are sending forty pull requests by hand, forever. Templates are fine for a two-day demo and fatal as a platform.

The blueprint should instead be a versioned module (Terraform module, CDK construct, or container image) that generated repositories reference. The repo the builder gets is a thin shell: a manifest, parameter values, and a pinned version. Upgrades become a dependency bump the platform can propose automatically.

blueprint.yaml — the contract every blueprint publishes
apiVersion: builder.cornell.edu/v1
kind: Blueprint
metadata:
  name: course-chatbot
  version: 2.3.1              # semver — deployments pin to this
  maintainer: ai-sei@cornell.edu
  maturity: supported          # experimental | supported | deprecated
summary: Teams chatbot answering from a document corpus.
matches:                       # what Plane 1 reads to route intent
  - "answer questions about my documents"
  - "chatbot for students / staff"
inputs:
  owner_netid:   { type: netid,  required: true }
  unit:          { type: unit_id, required: true }   # drives tenancy + billing
  corpus_source: { type: s3|sharepoint, required: true }
  audience:      { type: enum, values: [unit, cornell], default: unit }
provides:  [chat_endpoint, retrieval_api]      # composition contract — track D
requires:  [vector_store]
module:
  source: git::cornell/blueprints//course-chatbot
  ref: v2.3.1                  # referenced, never copied
cost:
  baseline_monthly_usd: 70
  scales_with: [queries, corpus_gb]
data_classification: [public, internal]   # blocks restricted data at the gate

Every other component reads this file. Plane 1 matches on matches and validates against inputs; Plane 3 enforces data_classification; Plane 4 binds unit to an account; Plane 5 tracks version for drift and cost for chargeback. Write this spec before writing anything else.

05Build sequence

Four phases over about a year. Each has an exit gate — if the gate isn't met, the next phase doesn't start, because the failure mode of platform projects is starting phase 3 while phase 1 is still broken.

P0
AUG 3–4

Prove the chain

One blueprint, one tenant, human review, no composition. Establishes that intent → repo → PR → pipeline → running service works end to end and that the room believes it. Scope is already correctly cut.

Gate: a live chain, and a written record of the artifacts and decisions that survives AWS leaving on Wednesday.
P1
SEP – NOV

Make it survivable

Convert the demo into something that can take a second user without a rewrite. This phase is unglamorous and non-negotiable: the manifest spec, module versioning, the GitHub App and propose_change, blocking policy checks, tenancy binding, and inventory written at deploy time. Three blueprints, three pilot units with real backlogs.

manifest v1semver modulesaccount vendingcfn-guard3 pilot units
Gate: a pilot unit deploys without AI-SEI touching a keyboard, and a version bump to a blueprint propagates to every deployment of it.
P2
DEC – MAR

Composition

The actual vision: separate blocks composed into one deployment. Requires the provides/requires contract from track D to be real — inter-block communication plus a proven isolation boundary between units. Dependency resolution, multi-block pipelines, and the self-service dashboard land here.

provides/requiresisolation proof8–10 blueprintsunit dashboards
Gate: a deployment composed of three independently versioned blocks, and a documented isolation test that a security reviewer signs off.
P3
APR – AUG

Self-service at scale

Open enrollment. The catalog stops being an AI-SEI artifact and becomes shared property: a contribution process, blueprint review standards, a maintainer model, chargeback, published SLOs, and the automated review agent replacing the human gate for low-risk changes.

contribution modelreview agentchargebackSLOs20+ blueprints
Gate: more than half of new blueprints in a quarter come from outside AI-SEI. If this fails, the platform is a bottleneck wearing a catalog costume.
P4
YEAR 2

The default path for all custom development

Extend well past AI-shaped things — SSO-protected web apps, API layers over systems of record, scheduled and event-driven jobs, batch data processing, UI hosting. Only now does a mandate make sense, because only now is the road demonstrably faster than the shortcut.

06Eight decisions needed before September

These are cheap to decide now and expensive to reverse later. Recommendations in green; each one has a real trade-off.

#DecisionRecommendationTrade-off you're accepting
D1Template copy or versioned module?Versioned module; repo is a thin shellMore upfront design and a harder authoring experience, in exchange for a patch path that doesn't require forty manual PRs.
D2How does intent match a blueprint?Whole catalog in model contextBreaks somewhere past 75–100 blueprints. Cheaper and more accurate than vector search until then; revisit, don't pre-build.
D3Who holds git credentials?GitHub App + propose_changeMore server-side plumbing than handing out scoped tokens, but it's the only version where "no direct write access" is actually true.
D4What triggers a deploy?Merge, and nothing elseSlower demos and no "just push it" escape hatch — which is the point. Two paths to production means the gate is optional.
D5Where is the tenancy boundary?Account per unit, not per deploymentWeaker blast-radius isolation than per-deployment accounts; far less account sprawl and simpler cost allocation. Revisit if a unit handles restricted data.
D6One IaC standard or three?Pick one for AWS; Terraform only for M365Someone's preferred tool loses. Three IaC dialects across a catalog is an unmaintainable authoring surface.
D7Build the portal or buy it?Build the catalog and gate; evaluate Backstage or Port for Plane 5Plane 5 is the least differentiated part and the most work. Buying it is not a defeat.
D8Who reviews, and how fast?Named rota with a published SLA (target < 4 business hours)A real staffing commitment. Without an SLA the review gate becomes the reason people route around the platform.
Prior art worth reading before D7

AWS built approximately this product — platform team owns templates, developers self-serve instances — and is exiting it. AWS Proton closed to new customers in October 2025 and support ends 7 October 2026. Building it yourselves is now the correct call, but Proton's template/instance versioning model is the best available reference for the problem in D1, and its commercial failure is a useful warning about how hard catalog adoption is.

07What it takes to run

A catalog with no maintainer is a graveyard within eighteen months. This is a staffing proposal as much as an architecture one.

10The ask

Three things, in order.

  1. Decide D1–D8 in September, before any Phase 1 code is written.
  2. Fund the P1 team — roughly 3.5 FTE for a quarter — and name a product owner. Not a committee.
  3. Recruit three pilot units with real, funded backlogs. Not volunteers who find it interesting; units that will be annoyed if it doesn't work.

Everything above is a proposal for discussion, not a plan of record. Cost figures are order-of-magnitude and need a real model before anyone commits to them.
